# Database Schema (DBML)

This section holds the working diagram of the rgs Postgres schema: tables, columns, enums and relationships. It's written in [DBML](https://dbml.dbdiagram.io/docs/) so it can be reviewed in PRs and drawn as an ER diagram on [dbdiagram.io](https://dbdiagram.io).

| File | What it is |
|---|---|
| [`rgs-schema.dbml`](https://github.com/wehnreptile/r1docs/blob/master/docs/backend/database/rgs-schema.dbml) | The **current** schema, matching Flyway migrations V1 → V4 |
| `proposals/<feature>.dbml` | Proposed changes, discussed before any migration is written (none yet) |

The Flyway migrations in `rgs/src/main/resources/db/migration` are the source of truth. This file is a readable map of them, not a replacement.

## Editing the layout on dbdiagram.io

dbdiagram.io lets you rearrange the tables yourself:

1. Open [dbdiagram.io/d](https://dbdiagram.io/d).
2. Paste the full contents of `rgs-schema.dbml` into the left pane.
3. The ER diagram renders on the right, with tables coloured by their `TableGroup`. Drag tables to tidy the layout. The layout is stored in dbdiagram.io only, not in this file.

## Keeping it current

- **Any PR that adds a Flyway migration also updates `rgs-schema.dbml`**, and bumps the version in the file header.
- **For a schema design**, copy the affected tables into `proposals/<feature>.dbml`, change them there, and get the proposal reviewed. Once the migration lands, fold the change into `rgs-schema.dbml` and delete the proposal.
- **Check the file parses** before pushing:

  ```bash
  npx -y -p @dbml/cli dbml2sql docs/backend/database/rgs-schema.dbml --postgres
  ```

## Conventions

- `created_at` / `updated_at` are `integer` epoch **seconds**, set by JPA `@PrePersist` / `@PreUpdate`.
- Order lifecycle timestamps (`orders.*_at`) and `search_history.searched_at` are `bigint` epoch **milliseconds**.
- Enum columns are Postgres enums. Each type is named after the Java enum's simple name in lowercase (e.g. `OrderStatus` → `orderstatus`), because Hibernate's `NAMED_ENUM` checks against that name.
- Surrogate primary keys are `GENERATED BY DEFAULT AS IDENTITY`.

## Domain map

Each group below is a `TableGroup` in the DBML file, drawn as a coloured area on dbdiagram.io. Groups only affect the diagram. Every table is in Postgres's `public` schema.

| Group | Tables | Role |
|---|---|---|
| user | `users`, `delivery_agents`, `address`, `search_history` | User identity and profile. One `users` row per (country code, phone, role), and delivery partners get an extra `delivery_agents` profile |
| store | `stores`, `assets`, `store_images` | Every physical store. `stores.corpus` says what kind of store it is |
| inventory | `drug_sku`, `pharmacy_drug_inventory` | Pharmacy master catalog, and per-store stock and price for it |
| cart | `cart`, `cart_item` | One cart per (user, store). Items point at master-catalog SKUs |
| order | `orders`, `order_items` | Orders keep a snapshot of the price paid |

When you add a table, put it in a group.

```
corpus master catalog (drug_sku)
        │
        ▼
store (stores.corpus) ──► store inventory (pharmacy_drug_inventory) ──► cart (user × store) ──► cart_item ──► drug_sku
```

A store can only sell SKUs that exist in its corpus's master catalog. Today only the pharmacy corpus has a catalog and inventory table.

## Known gaps in the current schema

These are listed so they aren't mistaken for intended design:

- `cart` has no unique `(user_id, store_id)`, and `cart_item` has no unique `(cart_id, sku_id)`.
- `pharmacy_drug_inventory` has no unique `(store_id, sku_id)`, and its `store_id` / `sku_id` are nullable.
- `cart_item.cart_id` and `cart_item.sku_id` are nullable.
- `order_items.sku_id` has no foreign key.
- `orders.delivery_agent_id` references `users.user_id`, not `delivery_agents.delivery_agent_id`.
- Money columns are `real` (float), not `numeric`.
- `cart_item`, `order_items` and `pharmacy_drug_inventory` are tied to `drug_sku`. Supporting a second corpus means generalising the catalog.
